# How Your Portfolio Site Works — Full Explanation

This walks through every file, in plain language, assuming zero prior
knowledge. Read it top to bottom once, then use it as a reference later.

---

## 1. The Big Picture

Your project has two halves:

- **The backend** (`index.js`) — a small program that runs on your computer
  (or a server) using Node.js. It does two jobs: (1) hands out your HTML/CSS/
  images to anyone who visits the site, and (2) listens for special requests
  like "save this contact message" or "update the profile" and reads/writes
  data to files on disk.
- **The frontend** (everything in `public/`) — the HTML, CSS, and
  JavaScript that actually run *inside the visitor's browser*. This is what
  people see and click on.

They talk to each other over HTTP. When your browser loads `about.html`, it
also runs `script.js`, which sends background requests (`fetch(...)`) to
your backend asking "what's the current profile data?" — the backend reads
`data/profile.json` and sends it back as a response.

```
Browser (frontend)  <---- HTTP requests ---->  index.js (backend)
  HTML/CSS/JS                                    reads/writes
                                                  data/*.json files
```

Nothing here uses a real database — `profile.json` and `messages.json` are
just text files that store data in a structured format called **JSON**
(JavaScript Object Notation — basically `{ "key": "value" }` pairs).

## 2. `package.json` — the project's ID card

```json
{
  "name": "my-portfolio",
  "main": "index.js",
  "scripts": {
    "start": "node index.js",
    "dev": "nodemon index.js"
  },
  "dependencies": {
    "express": "^5.2.1"
  }

```

- `"main": "index.js"` — tells Node "this is the file to run."
- `"scripts"` — shortcuts. Typing `npm start` runs `node index.js`.
  `npm run dev` runs it with **nodemon**, a tool that auto-restarts the
  server every time you save a file (handy while developing).
- `"dependencies": { "express": "^5.2.1" }` — this project needs the
  **Express** library (a popular toolkit for building web servers in
  Node.js) version 5.2.1 or compatible. Running `npm install` downloads it
  into a `node_modules/` folder.

`package-lock.json` is auto-generated by npm — it pins the *exact* versions
of every dependency (including dependencies of dependencies) so installs are
reproducible. You never edit it by hand.

## 3. `index.js` — the backend, explained block by block

```js
const express = require('express');
const path = require('path');
const fs = require('fs/promises');
```
Import three things:
- `express` — the web server toolkit.
- `path` — Node's built-in helper for building file paths that work on any
  operating system (Windows uses `\`, Mac/Linux use `/`; `path.join` handles
  that for you).
- `fs/promises` — Node's **f**ile **s**ystem module, the "promises" version,
  which lets you read/write files using `async/await` instead of old-style
  callbacks.

```js
const app = express();
const PORT = process.env.PORT || 3001;
```
`app` is your actual server object — everything below configures it.
`PORT` is which "door" the server listens on. `process.env.PORT` lets a
hosting provider override it; otherwise it defaults to `3001`, which is why
you visit `http://localhost:3001`.

```js
const DATA_DIR = path.join(__dirname, 'data');
const MESSAGES_FILE = path.join(DATA_DIR, 'messages.json');
const PROFILE_FILE = path.join(DATA_DIR, 'profile.json');
```
`__dirname` is a special Node variable meaning "the folder this file is in."
So these three lines build the full paths to your `data/` folder and the
two JSON files inside it, no matter where the project lives on disk.

### Middleware

```js
app.use(express.json());
app.use(express.urlencoded({ extended: true }));
app.use(express.static(path.join(__dirname, 'public')));
```
"Middleware" = code that runs on *every* incoming request before it reaches
your specific routes.
- `express.json()` — when a request arrives with a JSON body (like your
  contact form's `fetch` call), this reads it and makes it available as
  `req.body`.
- `express.urlencoded()` — same idea, but for traditional HTML form
  submissions.
- `express.static(...)` — this is the one that serves your HTML/CSS/JS/images.
  Any file inside `public/` becomes directly downloadable at the matching URL
  — e.g. `public/about.html` → `http://localhost:3001/about.html`,
  `public/cv.pdf` → `http://localhost:3001/cv.pdf`. This is *why* dropping
  `cv.pdf` into `public/` was enough to make the download links work — no
  extra route needed.

### Helper functions

```js
async function readJsonFile(filePath, fallback) {
  try {
    const raw = await fs.readFile(filePath, 'utf-8');
    if (!raw.trim()) return fallback;
    return JSON.parse(raw);
  } catch (err) {
    if (err.code === 'ENOENT') return fallback;
    throw err;
  }
}
```
Reusable logic so every route doesn't repeat itself: read a file as text
(`utf-8`), and turn it into a real JavaScript object/array with
`JSON.parse`. If the file is empty, or doesn't exist yet (`ENOENT` = "error,
no such entry"), return some `fallback` value instead of crashing.

```js
async function writeJsonFile(filePath, data) {
  await fs.mkdir(path.dirname(filePath), { recursive: true });
  await fs.writeFile(filePath, JSON.stringify(data, null, 2), 'utf-8');
}
```
The reverse: turn a JavaScript object back into text with
`JSON.stringify(data, null, 2)` (the `2` means "indent nicely with 2
spaces" so the file stays human-readable), and save it. `fs.mkdir(...,
{recursive: true})` makes sure the `data/` folder exists first, so it won't
crash on a fresh install.

### Contact routes

```js
app.post('/api/contact', async (req, res) => { ... });
```
This defines what happens when the browser sends a `POST` request to
`/api/contact` (that's what your `script.js` fetch call does when you
submit the contact form). Inside:

1. Pull `name`, `email`, `message` out of `req.body`.
2. Validate: all three must be present, and email must roughly look like an
   email (`/^[^\s@]+@[^\s@]+\.[^\s@]+$/` is a **regular expression** — a
   pattern that checks for "some characters, an @, more characters, a dot,
   more characters").
3. If invalid, respond with `res.status(400).json({ error: '...' })` — 400
   means "bad request," and the frontend shows that error message.
4. If valid, read the existing messages array, build a `newMessage` object
   with a unique `id` and timestamp, push it onto the array, and write the
   whole array back to `messages.json`.
5. Respond `res.status(201).json(...)` — 201 means "created successfully."

```js
app.get('/api/messages', async (req, res) => { ... });
```
A `GET` route (just reading, no submitting) that returns every saved
message as JSON — useful for you to check submissions by visiting
`http://localhost:3001/api/messages` in a browser.

### Profile routes

```js
const DEFAULT_PROFILE = { name: '...', title: '...', ... };
```
A backup/default profile object, used only if `profile.json` doesn't exist
yet (e.g. right after a fresh install, before you've ever saved anything).

```js
app.get('/api/profile', async (req, res) => {
  const profile = await readJsonFile(PROFILE_FILE, DEFAULT_PROFILE);
  res.json(profile);
});
```
Reads `profile.json` and sends it to whoever asked (your `script.js`, on
every page load).

```js
app.put('/api/profile', async (req, res) => {
  const current = await readJsonFile(PROFILE_FILE, DEFAULT_PROFILE);
  const allowedFields = ['name', 'title', 'bio1', 'bio2', 'quote',
    'location', 'graduating', 'currentlyLearning', 'openTo'];
  const updated = { ...current };
  for (const field of allowedFields) {
    if (typeof req.body[field] === 'string') {
      updated[field] = req.body[field].trim();
    }
  }
  await writeJsonFile(PROFILE_FILE, updated);
  res.json({ success: true, profile: updated });
});
```
`PUT` = "update." Loads the current profile, then for each allowed field,
if the request body includes a new value for it, overwrites it (`.trim()`
removes accidental leading/trailing spaces). The `allowedFields` whitelist
means someone can't sneak in arbitrary extra fields — only these nine are
ever saved. Then it writes the merged result back to disk and confirms.

### Fallback and startup

```js
app.use((req, res) => {
  res.status(404).send('404 - Page Not Found');
});
```
Any request that didn't match a route above (a typo'd URL, etc.) falls
through to here and gets a 404.

```js
app.listen(PORT, () => {
  console.log(`Server is running at http://localhost:${PORT}`);
});
```
Actually starts the server listening for connections, and prints that
confirmation message you see in your terminal.

## 4. `data/profile.json` and `data/messages.json`

These are pure data — no code. `profile.json` is a single JSON *object*
(curly braces, key-value pairs). `messages.json` is a JSON *array* (square
brackets, `[]`) holding one object per contact-form submission, each with
its own `id`, `name`, `email`, `message`, and `createdAt` timestamp. The
backend is the only thing that writes to these files — you could edit them
by hand too, since they're just text.

- `<nav>` is the top navigation bar, present on every page for consistency.

## 6. `script.js` — the frontend logic, explained block by block

```js

  "use strict";
  ...

```
Everything is wrapped in an **IIFE** (Immediately Invoked Function
Expression) — a function that runs itself right away. This just keeps all
your variable names contained inside this one function, so they don't leak

### Scroll reveal animation
```js

  const io = new IntersectionObserver(function(entries){
    entries.forEach(function(entry){
      if(entry.isIntersecting){
        entry.target.classList.add('in-view');
```

## 7. `style.css` — how the visual design is organized

The file is organized top to bottom in layers, roughly:

1. **`:root { --bg: ...; --accent: ...; }`** — CSS *variables* (custom
   properties). Instead of typing a color hex code everywhere, the whole
   site references `var(--accent)`, `var(--ink)`, etc. Change the value
   once at the top, and it updates everywhere that variable is used —
   this is how you'd redo the entire color scheme without touching any
   other line in the file.
2. **Global resets** — `*{ box-sizing: border-box; margin:0; padding:0; }`
   removes each browser's inconsistent default spacing so you start from a
   clean, predictable baseline.
3. **Base element styles** — `body`, `a`, `img`, `:focus-visible` — sets
   sensible defaults for basic HTML tags site-wide.
4. **Layout utility classes** — `.wrap` (centers content with a max width
   and side padding, reused on every page), `.nav-links`, etc.
5. **Component styles** — grouped by the piece of UI they belong to:
   buttons (`.btn`, `.btn-primary`, `.btn-secondary`), the contact form
   (`.contact-form`, `.form-row`), the about-page card (`.about-card`,
   `.fact-list`), skill chips (`.chip`), and so on.
6. **The additions I made** — `.nav-cv-btn` (shrinks the "Download CV"
   button to fit neatly in the nav bar) sits right after `.btn-secondary`
   since it's a variant of that button style.

The pattern to know for editing later: find the class name used in the
HTML (e.g. `class="fact-list"`), then search for `.fact-list{` in
`style.css` — that's where its appearance is controlled.

### 8.1 What is `fetch`, and where does it happen?

**In plain terms:** `fetch` is a built-in browser function for sending a
request to a server without reloading the page. Think of it like this — normally,
clicking a link makes your whole browser tab reload a new page. `fetch`
instead quietly sends a message in the background, waits for a reply, and
lets your JavaScript decide what to do with that reply (like updating text
on the page) — the visitor never sees a reload or a blank flash.

There are exactly **3 `fetch()` calls** in the entire project, all in
`public/script.js`:

---

**Fetch #1 — Line 64, sending the contact form**
```
64:      fetch('/api/contact', {
65:        method: 'POST',
66:        headers: { 'Content-Type': 'application/json' },
67:        body: JSON.stringify({ name: name, email: email, message: message })
68:      })
```
- **When does this line run?** Only when a visitor fills out and submits
  the contact form. It sits inside a function attached to
  `contactForm.addEventListener('submit', ...)` a few lines above (line 48)
  — so it does nothing at all until that exact click happens.
- **What does `method: 'POST'` mean?** HTTP requests come in a few "verbs."
  `POST` conventionally means "I'm sending you new data to create/save
  something." Compare to `GET`, which means "just give me data, I'm not
  sending anything to save."
- **What is `body: JSON.stringify(...)`?** The actual package being sent —
  the visitor's name, email, and message, converted from a JavaScript
  object into a plain text string (because that's the only format that can
  travel over a network request).
- **Where does it go?** To your own server, at the path `/api/contact` —
  which is `index.js` line 37 (see section 8.3 below).

---

**Fetch #2 — Line 144, loading the profile automatically**
```
144:  fetch('/api/profile')
145:    .then(function(res){ return res.json(); })
146:    .then(renderProfile)
147:    .catch(function(){ /* keep static fallback text already in the HTML */ });
```
- **When does this line run?** This is the one that's easy to miss because
  it's *not* inside a click handler or a form listener — it's just sitting
  in the main body of the script. That means it runs immediately, every
  single time `script.js` loads, on every page (Home, About, Achievements,
  Contact). That's why your nav logo updates with your saved name no matter
  which page you land on.
- **No `method` or `body` here — why?** Because this one defaults to
  `GET` (fetch's default when you don't specify a method), and a `GET`
  request has nothing to send — it's purely asking "what do you have?"
- **Where does it go?** `/api/profile` → matches `index.js` line 94.

---

**Fetch #3 — Line 182, saving the edit profile form**
```
182:      fetch('/api/profile', {
183:        method: 'PUT',
184:        headers: { 'Content-Type': 'application/json' },
185:        body: JSON.stringify(payload)
186:      })
```
- **When does this line run?** Only when the "Save Changes" button on the
  edit profile form is clicked — it's inside
  `editForm.addEventListener('submit', ...)` (line 163).
- **What does `method: 'PUT'` mean?** `PUT` conventionally means "update
  something that already exists" (as opposed to `POST`, which usually means
  "create something new"). That distinction is just a convention — it's
  `index.js`'s job to actually decide what each route does, but following
  the convention makes the code easier for other developers (including
  future you) to understand at a glance.
- **Where does it go?** Same URL as fetch #2 (`/api/profile`), but a
  different HTTP method — which is how `index.js` tells them apart (see
  section 8.3).

search for that exact same id (in quotes) inside `script.js` — that's every
place JavaScript is allowed to touch it.

### 8.3 What is a "route," and where do they happen?

**In plain terms:** a route is a rule the server sets up, meaning "if a
request comes in matching this exact URL and this exact HTTP method, run
this specific block of code." Your entire backend is really just a list of
these rules, checked top to bottom.

Every route in `index.js`, in the order they appear:

| Line | Code | Method + URL | What it does |
|---|---|---|---|
| 13 | `app.use(express.json())` | *(runs on every request)* | Reads JSON request bodies |
| 14 | `app.use(express.urlencoded(...))` | *(runs on every request)* | Reads traditional form bodies |
| 15 | `app.use(express.static(...))` | *(runs on every request)* | Serves any file inside `public/` directly — this is what makes `about.html`, `style.css`, `cv.pdf`, etc. downloadable/viewable |
| 37 | `app.post('/api/contact', ...)` | `POST /api/contact` | Saves a new contact message to `data/messages.json` |
| 69 | `app.get('/api/messages', ...)` | `GET /api/messages` | Returns every saved contact message |
| 94 | `app.get('/api/profile', ...)` | `GET /api/profile` | Returns the current profile data |
| 105 | `app.put('/api/profile', ...)` | `PUT /api/profile` | Updates the profile data |
| 134 | `app.use((req, res) => {...})` | *(catches anything unmatched above)* | Sends back "404 - Page Not Found" |
| 139 | `app.listen(PORT, ...)` | *(not a route — starts the server)* | Turns the server on and prints the confirmation message |

**Why does order matter?** Express checks routes top to bottom and stops at
the first match. That's why the 404 handler (line 134) is placed *last* —
if it were first, it would catch and reject every single request before any
real route got a chance to run.

**How a fetch call and a route connect, concretely:** fetch #3 above sends
`PUT` to `/api/profile` → Express scans its list of routes top to bottom →
skips the `POST /api/contact` one (wrong method and URL) → skips
`GET /api/messages` and `GET /api/profile` (wrong method) → finds
`app.put('/api/profile', ...)` on line 105 → runs that code. That's the
entire mechanism — no magic, just a list of if-this-then-that rules checked
in order.


## 9. Putting it all together — one full round trip

To make this concrete, here's exactly what happens when you click "Save
Changes" on the edit profile form:

1. Browser: form's `submit` event fires → `script.js` intercepts it with
   `e.preventDefault()`.
2. Browser: builds a `payload` object from the form fields, sends it as
   JSON via `fetch('/api/profile', { method: 'PUT', ... })`.
3. Network: the request travels to your running `index.js` server.
4. Server: `express.json()` middleware parses the JSON body into
   `req.body`.
5. Server: the `app.put('/api/profile', ...)` route reads the current
   `data/profile.json`, merges in the new values, writes the file back.
6. Server: responds with `{ success: true, profile: updated }` as JSON.
7. Browser: `script.js`'s `.then()` chain receives that response, calls
   `renderProfile(...)` to update the visible text on the page, shows
   "Profile updated successfully," and hides the form again.

Every other feature (contact form, profile GET on page load, CV download)
follows the same request → server → file → response → update-the-page
shape.
